Код на PyTorch работает на видеокартах NVIDIA, и его нужно перенести на GPU MetaX. Что именно
сломается — пока непонятно.

MXReady сначала читает код (только чтение, без запуска) и показывает места, которые с большой
вероятностью создадут проблемы: где напрямую вызывается компилятор NVIDIA, где жёстко заложены
группы по 32 потока (в MetaX их 64), где используется встроенный ассемблер, доступный только на
NVIDIA, где есть зависимость от библиотек, которые не будут работать. Для каждой находки указаны
файл, строка, причина и предложение по исправлению.

Он не переписывает ваш код и не выдаёт «процент совместимости» — количество сработавших правил
ничего не говорит о вероятности совместимости. Чистая статическая проверка означает лишь то, что
ничего очевидного не найдено; настоящий ответ даёт запуск того же коммита на машине MetaX.

> MXReady — это прототип сообщества, а не официальная сертификация совместимости от MetaX.
> Успешная статическая проверка **не** означает, что проект уже работает на MXMACA; окончательный
> ответ нужно получить, запустив тот же коммит в контролируемой среде с GPU MetaX.

## Что он делает

- Принимает публичные HTTPS-репозитории на GitHub и Gitee, при необходимости с указанием ветки, тега
  или 40-символьного коммита;
- Сканирует текстовые файлы Python, C/C++, CUDA, CMake, Shell, TOML, YAML и другие;
- Включает **35 правил** (`MXR-*`); каждая находка содержит путь к файлу, номера строк, сработавший
  фрагмент кода, рекомендацию и ссылку на первоисточник;
- Совпадения в тестах, примерах и документации считаются только подсказками: они всё равно попадают
  в отчёт, но из-за них весь проект не признаётся заблокированным;
- Выдаёт JSON, Markdown, SVG-значок и печатный HTML-отчёт (печать в PDF из браузера), а также пакет
  для удалённой проверки, зависящий только от стандартной библиотеки;
- Строго разделяет статические выводы и выводы проверки на реальном оборудовании;
- Предоставляет CLI только для чтения для локальных каталогов — удобно для офлайн-регрессии и
  генерации примеров отчётов;
- Опциональный `mxready-mcp`: предоставляет сканирование, статус задач, отчёты и поиск правил в виде
  5 инструментов Model Context Protocol для кодирующих агентов;
- Упаковывает одностраничный интерфейс на React и сервис FastAPI как единый развёртываемый блок.

Веб-интерфейс содержит страницы «Проверка исходного кода», «Пакетное сканирование», «История
сканирований», «Прогресс миграции», «Библиотека правил», «Доступ к MCP» и «Использование CLI»;
отчёты поддерживают переход к приоритетным файлам, поиск с пагинацией, сравнение и передачу,
чек-лист ручной проверки и HTML-экспорт для печати. MCP и Web должны явно использовать один и тот
же локальный каталог данных, чтобы читать отчёты друг друга.

MVP не включает частные репозитории, автоматическое переписывание исходного кода, оркестрацию Docker
для удалённых GPU-серверов, облачное планирование GPU, пользовательские аккаунты или процентную
«оценку совместимости».

## Что он нашёл в реальных проектах

Проверка [`NVIDIA/apex`](https://github.com/NVIDIA/apex) на коммите
`575968bc1f9127ccd61003a681472a83af4ff1a1`: **12 блокировок · 65 предупреждений · 140 подсказок**.
Полный отчёт — в [examples/reports/nvidia-apex.md](examples/reports/nvidia-apex.md).

Четыре наиболее характерных из 12 блокировок:

| Место | Совпадение | Почему это ломается на MetaX |
| --- | --- | --- |
| `csrc/welford.cu:36` | `#define WARP_SIZE 32` | Ширина warp жёстко задана как 32; в MetaX — 64 |
| `nhwc_batch_norm_kernel.h:1245` | `int lane_id = threadIdx.x & 31;` | lane 0 и lane 32 считаются одной и той же lane |
| `group_norm_nhwc.h:40` | `asm volatile("red.release.gpu.global.add.s32 …")` | Встроенный PTX привязывает код к бэкенду NVIDIA |
| `setup.py:65` | `subprocess.check_output([cuda_dir + "/bin/nvcc", "-V"])` | Напрямую вызывает `nvcc` для определения версии; в среде MetaX такой команды нет |

Два из четырёх **успешно компилируются**, но арифметика lane и ширина warp дают неверные результаты
на 64-канальных wave, и тесты могут это не покрыть; остальные два просто не компилируются на MetaX.
Оба вида проблем могут растянуть миграцию на недели.

Ещё два примера с закреплёнными коммитами дополняют доказательства с обеих сторон цикла
«диагностика блокировок — исправление»:

- [`bitsandbytes`](https://github.com/bitsandbytes-foundation/bitsandbytes) (`a616886`): 27 находок,
  7 блокировок; отчёт — в [examples/reports/bitsandbytes.md](examples/reports/bitsandbytes.md).
- [`causal-conv1d`](https://github.com/Dao-AILab/causal-conv1d) (`cd81f04`): после исправлений по
  отчёту число находок снизилось, а проверка на реальном оборудовании на MetaX C500 показала все
  `passed`; см. [записи по кейсу миграции](docs/migration-case-2026-11.md).

## Архитектура

```text
React/Vite UI
      │ /api
      ▼
FastAPI ── очередь задач и отчёты на SQLite
   │
   ├─ атомарное взятие / heartbeat аренды ── ограниченный Git fetch ── индекс файлов только для чтения ── движок правил на YAML
   ├─ отчёты JSON / Markdown / SVG
   └─ ZIP для проверки ◀── запускается на вашем хосте MetaX ── result.json
```

Веб-сервис никогда не импортирует, не устанавливает, не собирает и не выполняет код из
сканируемого репозитория. Удалённый runner запускается только на машине под вашим контролем и
требует явного подтверждения перед выполнением любой команды проекта.

Python-код целиком расположен в `src/`; правила по умолчанию и схема проверки поставляются вместе с
установленным пакетом. Соглашения о каталогах, очередь задач и примечания об обновлении описаны в
[руководстве по архитектуре](docs/architecture.md). После изменения моделей выполните
`make contracts`, чтобы заново сгенерировать контракты интерфейсов.

| 35 правил `MXR-*` | Доступно | Для каждого правила есть положительный и похожий отрицательный фикстурный пример |

| Панель прогресса миграции (агрегация по репозиториям, тренды блокировок) | Доступно | Тесты агрегации на бэкенде + Vitest |
| Пакет для проверки и runner только на стандартной библиотеке | Доступно | Регрессия установщика + тесты границ безопасности |
| Установочные ZIP для трёх платформ и wheel/sdist с веб-интерфейсом | Доступно | Release-воркфлоу реально устанавливает и запускает на Windows / Linux / macOS |
| Одностраничный интерфейс на React | Доступно | Vitest + строгий режим TypeScript |
| Пакетная оценка (`mxready-scan-batch`) | Доступно | CLI-регрессия |
| Инструменты MCP (`mxready-mcp`, требуется `.[mcp]`) | Доступно | Тесты бэкенда и реальное рукопожатие по stdio |
| Проверка на реальном GPU MetaX | Выполнены две обезличенные проверки (MetaX C500: `pytorch/extension-cpp` @ `1c325b2`, `causal-conv1d` @ `cd81f04`) | Все пять средовых проверок `inspect` runner и однокарточный smoke — `passed`; сборка causal-conv1d использовала временный патч, не отправленный в апстрим, каждому другому проекту нужна собственная проверка |

Инженерное состояние: `ruff`, `mypy`, проверка контрактов и `pytest` — всё зелёное (более 540
тестов, покрытие веток 90%); CI покрывает Python 3.11 / 3.12 / 3.13 × Windows / Linux / macOS,
плюс job runner на Python 3.10.

## Известные ограничения

- **Никаких выводов о совместимости.** Все результаты ограничиваются сигналами статического риска и
  рекомендациями для ручной проверки; утверждение вроде «проверено в среде MetaX» должно быть
  привязано к конкретному коммиту, получено как результат `verified` на контролируемом GPU MetaX и
  быть не старше 30 дней.
- **Точность правил не откалибрована статистически на большом числе реальных проектов.**
  Положительные и отрицательные примеры взяты из контролируемых фикстур и перепроверены на
  публичных репозиториях (0 ложных срабатываний); систематические уровни ложных срабатываний и
  пропусков всё ещё требуют статистики по большему числу реальных проектов, см.
  [руководство по правилам](docs/rules.md).
- **Результаты проверки действительны 30 дней**; по истечении срока статус отчёта становится
  `stale`, и результат нужно загрузить заново.
- **Границы MVP**: без частных репозиториев, без автоматического переписывания исходного кода, без
  облачного планирования GPU, без пользовательских аккаунтов, без процентной оценки совместимости.

> Примеры отчётов по публичным проектам — в [examples/reports](examples/reports):
> `pytorch-extension-cpp` проходит всё (4 подсказки), `nvidia-apex` (12 блокировок) и
> `bitsandbytes` (7 блокировок) в состоянии блокировки, а `causal-conv1d` сохраняет обе версии — до
> и после исправления. Они приведены рядом, чтобы показать: отчёты действительно бывают зелёными и
> действительно бывают красными. Процесс удалённой проверки описан в
> [examples/verification/README.md](examples/verification/README.md).

## Установка и запуск

Обычным пользователям достаточно установить релизный пакет с веб-интерфейсом: Node.js, PyTorch и
драйверы GPU не нужны. На всех трёх платформах должны быть предварительно установлены
**Python 3.11+ (с pip/venv) и Git**; при первой установке зависимости Python по умолчанию
загружаются из сети.

| Платформа | Пакет | После распаковки выполнить в каталоге пакета |
| --- | --- | --- |
| Windows 10/11 | `mxready-1.0.1-windows.zip` | PowerShell: `.\install.ps1`, затем `.\start.ps1` |
| Linux | `mxready-1.0.1-linux.zip` | `bash install.sh`, затем `bash start.sh` |
| macOS (Apple Silicon / Intel) | `mxready-1.0.1-macos.zip` | `bash install.sh`, затем `bash start.sh` |
| Управляемое окружение Python | `mxready` на PyPI | `python -m pip install mxready`, затем `mxready-serve` |
| Существующее окружение Python | `mxready-1.0.1-py3-none-any.whl` | в выделенном venv: `python -m pip install <путь к wheel>`, затем `mxready-serve` |

После запуска откройте <http://127.0.0.1:8000>; для остановки сервиса нажмите `Ctrl+C` в терминале.
ZIP-архивы — это пакеты приложения на Python: они не включают Python или Git и не являются
нативными пакетами EXE/DMG или установщиками системных пакетных менеджеров. Опубликованные
вложения — на [GitHub Releases](https://github.com/shuljyli/MXReady/releases); офлайн-подготовка,
проверка контрольных сумм, обновление, удаление и устранение проблем в Windows описаны в
[руководстве по установке и выпуску](docs/installation.md) (на китайском языке).

Мейнтейнеры, собирающие релизные пакеты: установите зависимости для разработки, затем выполните
`make release` (Windows: `.\scripts\make.ps1 release`); артефакты попадают в игнорируемый Git
каталог `dist/`. Развёртывание на сервере (bare metal / systemd / Docker / nginx) и параметры
конфигурации `MXREADY_*` описаны в [руководстве по развёртыванию](docs/deployment.md) и
[.env.example](.env.example).

### Разработка из исходного кода

Требования: Python 3.11+, Git и Node.js 22+ (нужен только для разработки/сборки фронтенда).

```bash
make install                # создать .venv, установить зависимости для разработки, npm ci (Windows: .\scripts\make.ps1 install)
bash ./scripts/dev.sh       # запуск фронтенда и бэкенда одной командой (Windows: .\scripts\dev.ps1)
```

`dev.sh` / `dev.ps1` одновременно запускают фронтенд <http://localhost:5173> (`/api`
проксируется на бэкенд) и бэкенд <http://127.0.0.1:8000> (горячая перезагрузка `--reload`). В
режиме разработки используйте порт 5173; бэкенд отдаёт полный интерфейс, если `frontend/dist` уже
существует, документация API находится на `/docs`, а руководство API на китайском языке — в
[docs/api.md](docs/api.md).

Единые точки входа команд (`install` / `dev` / `frontend` / `test` / `lint` / `typecheck` /
`build` / `release` / `clean`):

| Задача | Windows (PowerShell) | Linux / macOS | Что делает |
| --- | --- | --- | --- |
| Установка зависимостей | `.\scripts\make.ps1 install` | `make install` | venv + зависимости бэкенда + `npm ci` |
| Запуск бэкенда | `.\scripts\make.ps1 dev` | `make dev` | uvicorn `--reload`, порт 8000 |
| Запуск фронтенда | `.\scripts\make.ps1 frontend` | `make frontend` | Vite dev, порт 5173 |
| Запуск тестов | `.\scripts\make.ps1 test` | `make test` | pytest бэкенда (с порогом покрытия) |
| Линтинг | `.\scripts\make.ps1 lint` | `make lint` | ruff по src / scripts / tests / packaging |
| Проверка типов | `.\scripts\make.ps1 typecheck` | `make typecheck` | mypy по src / scripts |
| Сборка фронтенда | `.\scripts\make.ps1 build` | `make build` | `npm run build` создаёт `frontend/dist` |
| Сборка релизных пакетов | `.\scripts\make.ps1 release` | `make release` | UI + wheel/sdist + ZIP для трёх платформ в `dist/` |
| Очистка | `.\scripts\make.ps1 clean` | `make clean` | удаляет `.pytest-temp` |

Подробное использование и соглашения о кодах выхода для `mxready-scan` (локальные каталоги),

## Значения статусов

| Статус | Значение |
| --- | --- |
| `passed` | Не найдено блокировок или предупреждений; проверка на реальном оборудовании всё ещё требуется |
| `warnings` | Риски миграции, требующие ручной проверки |
| `blocked` | Есть блокировки, которые следует устранить до запроса удалённых вычислительных ресурсов |
| `not-run` | Результат проверки в среде MetaX ещё не загружен |
| `verified` | `mx-smi` и проверка устройств PyTorch прошли для того же коммита, все средовые проверки успешны, а результат не старше 30 дней; это не то же самое, что полная сертификация проекта |
| `failed` | Команда проверки завершилась ошибкой |
| `stale` | Результату проверки больше 30 дней, требуется повторный запуск |

Отчёты намеренно не дают процентную оценку совместимости, потому что количество сработавших правил
не может отражать вероятность совместимости проекта.

## Границы безопасности

- Разрешены только публичные HTTPS-репозитории на `github.com` и `gitee.com`; Git никогда не читает
  учётные данные, не загружает LFS-объекты и не инициализирует подмодули, а получение имеет
  ограничения по времени и размеру/числу объектов;
- Веб-сканирование никогда не выполняет код репозитория; результаты проверки ограничены 1 МиБ и
  привязаны к сканируемому коммиту;
- Runner никогда не использует `sudo` и не устанавливает ПО; команды выполняются с `shell=False`,
  а команды проекта требуют ручного подтверждения перед выполнением;
- Перед публичным развёртыванием включите ограничение частоты запросов и ограничение размера тела
  запроса.

Перед развёртыванием полностью прочитайте [модель безопасности](docs/security.md) и
[руководство по runner](docs/runner.md).
