## 1. 本轮判断

下一轮优先把“扫描了哪份源码、真机运行了哪个构建产物、发布了哪一批安装包”串起来，
再扩大规则回归范围、补服务运行保障和使用体验。

原因是项目已经有扫描、整改、报告对比、CI 基线、MCP 与真机案例。继续增加入口的收益，
暂时低于解决现有结果的可追溯性问题。初次复核已在隔离临时仓库中复现一处问题：
同一个 HEAD 下修改 CUDA 文件，本地扫描从零发现变成一个 blocker，但报告的提交和
`scan_id` 完全相同。后续已修复扫描 ID 复用和文件覆盖，来源元数据仍按 MXP-01 推进。

## 3. P0：先补结果的来源与验收

### MXP-01：本地报告要能区分提交与工作区

**问题与证据。** [本地扫描 CLI](../src/mxready/cli/scan_repository.py)读取 HEAD 和 origin，
但分析的是当前目录内容；显式 `--commit` 也只做格式校验。
初稿时 `scan_id` 由 URL 与提交生成，输出文件名只包含仓库名与提交前缀，
未提交修改、不同规则配置下的重扫会共用身份并覆盖同名报告；该身份复用与覆盖问题已修复。

本次临时仓库复现：先提交 `int value = 0;`，再只把工作区文件改成
`#define WARP_SIZE 32`；两次均省略 `--commit`。退出码由 0 变成 2，
blocker 数由 0 变成 1，但提交与扫描 ID 相同。输入、报告均在临时目录，已随检查结束清理。
这说明存在来源歧义，不代表 Web 固定提交获取路径也有相同问题。

**实施内容。**

1. 定义来源元数据，至少区分干净 Git 提交、带本地修改的目录、无 Git 的显式声明目录；
   记录实际 HEAD、工作区状态及扫描输入摘要。摘要只描述纳入分析的文件集合，不能称为完整仓库证明。
2. 保留本地检查未提交改动的用途，明确标注工作区快照；显式提交与实际 HEAD 不一致时，
   拒绝把它作为已核对的提交报告。无 Git 目录继续允许显式声明，但不伪装成已核对来源。
3. 分离“仓库提交”“扫描执行 ID”“内容/分析条件摘要”，避免把一次工作区修改归入同一报告。
   输出文件采用不会静默覆盖的命名或显式覆盖选项，覆盖 JSON、Markdown、SARIF、SVG 和批量 CSV 引用。
4. 基线 CI 与验证包明确处理来源不完整的情况。新增严格策略对未知来源失败关闭；
   历史报告仍能读取，标为来源未知，不直接破坏既有 JSON 消费方。

**验收。** 干净检出、暂存修改、未暂存修改、未跟踪源码、非 Git 目录、错误显式提交、
同提交不同分析配置均有回归。变更后的快照身份和文件不与原报告混淆；旧报告可读取；
Web、CLI、MCP 和各导出展示一致。涉及模型修改时同步生成契约。

### MXP-02：真机结果关联到实际测试的构建产物

**问题与证据。** [causal-conv1d 案例](migration-case-2026-11.md)记载：应用补丁构建 wheel，
随后恢复干净 checkout，再运行 smoke。[结果](../examples/verification/causal-conv1d/result.json)
记录了上游提交和干净状态，但没有结构化保存补丁摘要、wheel 摘要及导入模块来源。
因此，现有记录能说明该环境中的 smoke 通过，不能仅凭干净 checkout 证明安装的二进制来自未修改的上游代码。

**实施内容。**

1. 定义独立的构建证据清单，关联上游提交、补丁 SHA-256、补丁后源码标识、构建命令和日志、
   wheel SHA-256、Python/PyTorch/MACA 版本；原始失败记录和既有通过结果均保留。
2. probe 记录实际导入模块位置和可核对的模块文件/安装包信息，关联构建清单摘要。
   本机路径按既有规则脱敏；摘要是关联信息，不宣称可信执行或供应链认证。
3. 新案例优先使用包含迁移改动的本地提交作为扫描与构建基线，保留与上游的关系；
   来源尚未提交上游时明确说明。不能通过恢复文件来省略构建时实际采用的补丁。
4. 采用可选、版本化的证据扩展；旧 runner 结果继续可读，界面区分“旧结果未采集来源”
   与“新结果来源已记录”。另验收生成验证 ZIP 在 Python 3.10 上的完整项目命令路径，
   不扩大宿主 wheel 的 Python 支持声明。

**验收。** 在受控测试中安装另一个来源的同名模块时，能显示来源不匹配或未知，
不能显示为已完成构建关联。拿到 C500 后重新采集一条包含补丁、构建和运行关联的真实记录；
记录数值比对范围，不把 smoke 扩写成完整测试或性能通过。无设备时软件回归可完成，真机项保持待执行。

### MXP-03：按候选整理发布证据，并核对已发布内容

**问题与证据。** [发布验收](release-acceptance.md)已经规定六组安装、真实断网、
双进程故障、真实旧库和硬件分项。当前工作流配置不能证明最新候选已全部通过。
本地 2026-11-04 的验收记录对应 `538b834…`，只能证明那次 macOS 安装和已记录检查，
不能作为本次同步后主分支的验收结论。

发布作业遇到 PyPI 同版本 HTTP 200 会跳过上传，目前未比较远端文件摘要。
版本已存在与内容一致是两回事，应在保留补打标签用途的同时显示实际差异。

**实施内容。**

1. 建立候选台账，逐项记录完整提交、版本、产物摘要、执行环境、命令、日志、结果与未覆盖项；
   状态采用待执行/通过/失败/受外部条件阻塞，不能用源码测试填补安装或硬件项。
2. 同一批产物完成 Windows/Linux/macOS × Python 3.11/3.12 安装；另执行 Windows/Linux
   普通用户、准备 wheelhouse 后真实断网检查。保持 `--no-index` 与系统断网的区别。
3. 将双服务杀进程和真实旧库升级/恢复分别保存时间线；真实旧库不可得时保留缺项，
   构造 schema 测试仍作为回归使用。
4. PyPI 已有版本时，比对 wheel/sdist 文件名与 SHA-256，再决定跳过或报告冲突。
   同版本内容冲突不覆盖远端、不静默成功，应明确采用远端已发布候选或递增版本。
   不假设重新构建必然得到相同字节。
5. GitHub Release、PyPI、GitLink 镜像分别核对存在的附件与摘要；镜像核对沿用
   [既有方案](gitlink-mirror.md)，不在本任务中配置账户或推送镜像。
   工作流证据按当前 7/30 天保留设置及时归档；GitHub 的 artifact 会到期，
   不能把临时下载地址当作长期证据。[官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

**验收。** 一个候选有可追溯的总表和分项日志，缺项明确可见；同版本同摘要可跳过，
不同摘要和缺失文件有失败回归。未实际查询的 Release、PyPI 和镜像状态不能填写“已核对”。
完整门槛通过前，只描述已取得的证据。

## 4. P1：提升规则质量与运行保障

### MXP-04：从七个片段扩展到有上下文的语料

**问题与证据。** [语料清单](../tests/fixtures/corpus/reviewed.json)为 7 个真实片段。
[评估脚本](../scripts/evaluate_rule_corpus.py)检查标注信号，不代表全仓库精度；
单独评估片段也不覆盖路径降级、跨文件工具链画像、事实提取与完整分析流程。

**实施内容。** 第一批目标为不少于 30 个经复核案例，来自不少于 5 个固定提交项目；
优先覆盖四条 blocker 规则，以及 nvcc 探测、架构参数、cu-bridge、文档字符串和测试路径。
每个重点风险增加相似反例；为上下文判断加入多文件最小仓库，保留原始信号与最终报告两层断言。
记录来源提交、blob/片段摘要、许可或引用依据、预期级别与人工理由。

评估结果按规则、正反例和最终级别分组，单列未标注命中；评估脚本校验清单结构、重复 ID、
未知规则和必要来源字段。新增误报先保存失败回归，再调整规则；新规则仍须一手资料。

**验收。** 扩展集离线运行，已标注项无未解释回归；预过滤开关两种模式命中一致。
缺少样本的规则明示空缺。30 个案例是首批工作量目标，不是统计准确率门槛，
不从该集合推导总体误报率或兼容率。

### MXP-05：让执行时限与服务诊断可验证

**问题与证据。** [规则引擎](../src/mxready/scanning/rule_engine.py)在规则、文件与命中边界检查预算，
单次 `re.finditer` 阻塞时不能由该检查及时打断；[worker](../src/mxready/services/worker.py)
在线程中运行，退出等待 `join()` 没有上限。[健康接口](../src/mxready/app.py)只返回状态与版本。
这是已知机制边界，尚未在本次证明默认规则能触发服务卡死。

**实施内容。**

1. 在受控外层子进程中构造超时、异常退出、租约丢失与慢 Git 场景，先取得时间和资源基线。
2. 对比可终止子进程隔离与受限匹配方案，再确定实现；优先验证由父进程持有租约及写库、
   分析子进程只返回结果的可行性。终止超时执行后拒绝迟到写入，清理其临时资源。
3. 明确整体扫描时限、退出宽限与失败代码；中断仍为明确失败并要求重扫，
   不在本项顺带引入自动任务重放。
4. 保留现有 `/api/health` 兼容行为，增加独立就绪检查和脱敏诊断，覆盖 SQLite 查询、
   消费者存活与队列状态。队列满属于准入问题，不直接判断整个服务失活。
5. 复用结构化日志补充阶段耗时、排队时间、失败代码和中断次数；默认不公开仓库名、
   本机路径、令牌或命令参数，不要求引入整套外部监控服务。

**验收。** 在固定夹具和已记录配置下，超时任务于配置总时限加不超过 5 秒清理宽限内结束；
退出在配置宽限内完成；后续任务可处理，过期令牌写入被拒。双真实进程演练保留证据，
不以线程测试替代。正常输入的命中集合保持一致，性能差异单独记录后确定可接受范围。

### MXP-06：把现有备份方法做成可演练的操作

**问题与证据。** [SQLiteStore](../src/mxready/persistence/sqlite.py)已有 `backup()` 和
`prune_old_scans()`，[部署文档](deployment.md)也说明了在线备份。
当前可选清理在服务启动时执行，默认保留历史；缺的是统一操作入口、预览和恢复验收。

**实施内容。** 增加本机运维 CLI，复用在线备份 API，生成源版本/schema、时间、摘要与备份结果；
拒绝静默覆盖既有备份。恢复先在独立目录核对完整性与报告数量，再按停服流程切换。
清理增加 dry-run，展示会删除的终态扫描和关联记录数；执行前要求显式确认，保护排队与活跃租约。
既有 `SCAN_RETENTION_DAYS` 默认值和启动清理语义不在本轮悄然改变。

在线库备份继续使用 SQLite API；SQLite 将完成的备份描述为数据库快照，
符合当前 `backup()` 的复用途径。[官方说明](https://www.sqlite.org/backup.html)

**验收。** 包含报告、验证历史、人工清单与复核记录的备份能在隔离目录完整恢复；
坏文件、目标不可写、目标已有文件及并发写入场景有回归。
恢复检查对所有导出重新推导验证有效期；超过 30 天的结果仍为 stale。
真实旧版本库升级与恢复仍需另做，不将新建测试库当作历史数据。

## 5. P2：在可靠性基础上改善使用

### MXP-07：批量恢复与发现复核

**问题与证据。** [批量页](../frontend/src/components/BatchScans.tsx)已避免重提状态不明的 POST，
但仍需人工到历史中查找。[复核组件](../frontend/src/components/FindingReviews.tsx)
通过全报告下拉框选发现，大报告中容易脱离用户当前筛选位置。

**实施内容。**

- 扫描提交支持可选幂等键，由服务端原子保存键、规范化请求摘要与任务 ID。
  同键同请求返回原任务，同键不同请求冲突；复用已有任务不重复占用扫描准入名额。
  设计键保留时间与任务清理关系，过期后提示状态未知，不能自动当作新请求。
- 批量页在发出请求前持久化键；网络丢失或刷新后由用户显式恢复同一次提交。
  保留现有“请求结果不明不自动重提”的行为。服务仍无账号隔离，不把键当成身份凭证。
- 从发现卡片直接进入相应复核，报告筛选与分页后仍绑定 scan/rule/path；
  展示最新复核状态并可查看追加历史，保存失败保留理由输入。

**验收。** 覆盖并发同键、响应丢失、刷新、请求不匹配、限额和过期键；不产生重复任务。
发现筛选、换页、切换扫描时不串写复核记录；保存后静态结果、硬件状态和 CI 基线判断均不变。
保留键盘操作、可访问名称和 320 像素窄屏回归。
